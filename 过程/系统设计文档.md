## 一、提示词层

### 1.1 核心原则：渐进式披露 + 服务器分发

- 每个 LLM 请求只收 60-80 行指令，细则和理论放独立 prompt，Agent 按需查阅
- **理论使用分为三层：框架层（必内联，60-80行/维度）> 评分层（预取缓存）> 理论层（纯按需）**
- **所有 prompt 文件不打包进客户端，不在用户电脑上落盘**——启动时从服务器拉取，Worker 内存中持有
- 服务器同时负责收费验证和 prompt 分发，服务器不可达则应用无法启动（已有 license validate 守门）

### 1.3 客户端 prompt 传递链路

```
应用启动
  │
  ├── 1. 输入启动码 → POST /subscriptions/validate → 有效 → 进入主界面
  │
  ├── 2. Electron 调 IPC PROMPTS_FETCH_ALL
  │       → GET /prompts/groups → 遍历每组 GET /prompts/groups/:id/versions
  │       → 全部存入内存 promptCache: Map<string, PromptCacheItem>
  │
  ├── 3. Electron spawn growthplan_worker.exe
  │       → 通过 stdin 发送 {type: "init_prompts", prompts: {...完整bundle...}}
  │
  └── 4. Worker 收到 init_prompts
          → PromptStore 存内存
          → 后续所有 LLM 调用通过 prompt_store.get("code") 获取
```

### 1.4 Worker 侧 PromptStore

```python
class PromptStore:
    """提示词内存存储，从 Electron 接收，不读任何文件"""

    def __init__(self):
        self._prompts: dict[str, str] = {}       # groupCode → content
        self._versions: dict[str, int] = {}      # groupCode → version

    def load_from_bundle(self, bundle: dict):
        """Electron 发来的完整 prompt 包"""
        for code, item in bundle.items():
            self._prompts[code] = item["content"]
            self._versions[code] = item["version"]

    def get(self, code: str) -> str:
        """获取指定提示词的 content，不存在则抛异常"""
        if code not in self._prompts:
            raise PromptNotFoundError(
                f"提示词 '{code}' 未加载。服务器不可达时应用无法启动，"
                f"此错误不应出现在正常运行中。"
            )
        return self._prompts[code]

    def get_version(self, code: str) -> int:
        return self._versions.get(code, 0)

    def get_all_versions(self) -> dict[str, int]:
        return dict(self._versions)
```

### 1.5 版本管理

- 每次分析结果中记录全部 prompt 版本指纹：`_meta.prompt_versions = {"interaction": 3, ...}`
- 后台更新 prompt 内容 → 用户下次启动自动拉最新版本
- 可选：定时轮询后台检查版本变更，支持不重启热更新

### 1.6 安全性

- prompt 内容不在用户电脑上落盘，只在内存中
- Worker 的 stdin 通信是进程内通道，不经过网络
- 服务器不可达 → license validate 先拦截 → 应用根本进不去

## 二、Worker 进程架构

### 2.1 核心决策

- **单 Worker 进程**：review pipeline 和 Q&A agent 共享同一个 Python 子进程，共享 LLM Client、LanceDB 连接、缓存
- **不装 PyTorch**：embedding 走 LLM API（text-embedding-3-small），不给用户电脑塞模型文件
- **PyInstaller 打包**：`growthplan_worker.exe` 单文件，零依赖部署

### 2.2 Worker 启动流程

```
Electron spawn growthplan_worker.exe
    ├── 等待 stdin 收到 {type: "init_prompts", prompts: {...}}
    │   └── PromptStore.load_from_bundle() → 内存持有所有提示词
    ├── 连接 LanceDB（确认索引可用）
    ├── 连接 SqliteSaver（检查是否有未完成的复盘任务）
    └── 进入消息循环
        ├── "run_review" → LangGraph invoke（带 checkpoint）
        │   ├── 各节点用 prompt_store.get("code") 获取 system prompt
        │   ├── 每个 LLM 调用：先查缓存 → 没命中才调 API
        │   ├── 每次 API 调用后：记录 token 用量 + 费用
        │   ├── 每个节点完成后：emit 结构化事件
        │   └── 全部完成后：建 LanceDB 索引 + 触发 hooks
        ├── "init_qa" → 构建 Agent（共享同一个 LLM client + LanceDB + PromptStore）
        ├── "ask" → 路由到对应模块 Agent（带滑动窗口记忆）
        └── "test_dimension" → 单次分析（不写索引）
```

**关键变化**：Worker 不再 `open("file.md").read()`，改为收 Electron 发来的 prompt bundle。删除所有本地文件读取逻辑。

### 2.3 进程守护

Electron 侧监控 Worker 进程状态。Worker 崩溃 → 自动重启 → 从 LangGraph checkpoint 恢复未完成的任务（最多重试 3 次）。

## 三、Review Pipeline（复盘流水线）

### 3.1 流水线总览

```
原始直播数据 → Pre-flight 费用预估 → 用户确认
    │
    ▼
Step 1: 数据分片（1 次 LLM 调用）
    输出: N 个片段
    守卫: 片段数 < 1 → 早停
    Schema 校验: Pydantic → 失败 auto-fix retry（3次）
    │
    ▼
Step 2: 单片段 × 单维度分析（N×6 次，并行 + 限流）
    并发控制: asyncio.Semaphore(max=8)，429 退避重试
    缓存优先: 先查 LLMCache，命中跳过 API
    6 个维度子 Agent，各有独立工具集
    │
    ▼
Step 3: 维度汇总（6 次并行 LLM 调用）
    每个维度合并 N 个片段 → 综合评分 + 趋势 + P0/P1/P2
    │
    ▼
Step 4: 教练报告（1 次 LLM 调用）
    合并 6 维度汇总 → 9 章节报告
    ⚠️ 个人状态 < 3 → 唯一输出"建议休息"
    │
    ▼
后处理: 存储(不可变版本) + 费用记录 + 建 LanceDB 索引 + 触发 Hooks
```

### 3.2 Step 2 维度子 Agent

每个维度是一个独立的子 Agent，有自己的角色设定和工具：

| 维度 | Agent 角色 | 工具（框架已内联） |
|------|-----------|------------------|
| 互动效果 | 互动效果顾问 | 评分细则(预取), 示例库(按需), read_theory(备选) |
| 粉丝关系 | 粉丝关系顾问 | 评分细则(预取), 示例库(按需), read_theory(备选) |
| 流水营收 | 营收分析顾问 | 评分细则(预取), 示例库(按需), read_theory(备选) |
| 内容质量 | 内容策划顾问 | 评分细则(预取), 示例库(按需), read_theory(备选) |
| 个人状态 | 身心健康顾问 | 评分细则(预取), 示例库(按需), read_theory(备选) |
| 人设定位 | 人设定位于顾问 | 评分细则(预取), 示例库(按需), read_theory(备选) |

### 3.3 输出格式

每个 issue 必须附带：
- severity（轻度/中重度/严重）
- confidence（high/moderate/low）
- change_difficulty（低/中/高）
- change_impact（低/中/高）
- tiny_first_step（30秒内可执行的最小改进动作）

### 3.4 全局约束（12 条）

1. 所有判断必须有数据支撑（时间戳 + 原文），不得空泛评价
2. 评分必须附带评分依据
3. 建议必须可执行可落地（具体话术或步骤）
4. 推测部分标注置信度（high/moderate/low）
5. 人设与表现不一致时标注"人设-表现偏差"
6. 不和别的 V 比较，只和自己历史比较
7. 任一维度评分 < 5 分 → 必须给出 P0 级别改进建议
8. 所有输出格式统一（JSON Schema）
9. 人设信息不完整 → 降级为无人设处理
10. 区分"本周可做 / 需练习周期 / 需长期积累"三个时间尺度
11. 综合报告只推荐一个本周焦点
12. 禁止临床诊断术语，语气如教练不如老师、如朋友不如家长

## 四、Q&A 系统（四大功能模块）

### 4.1 架构

```
Q&A 面板
    │
    ▼
消息路由器（关键词规则，不需要调 LLM）
    ├── "review"   → 模块 1: 复盘问答
    ├── "persona"  → 模块 2: 人设工坊
    ├── "practice" → 模块 3: 刻意练习
    ├── "topic"    → 模块 4: 话题引擎
    └── "mixed"    → 多模块串联回答
```

每个模块是独立的 ReAct Agent，有自己的 system prompt 和工具集，互不共享。

### 4.2 模块 1：复盘问答

**定位**：解读分析报告、对比历史数据、解答具体评分问题。

**工具（4个）**：
- `lookup_chunk_detail` — 查片段所有维度评分
- `get_dimension_report` — 查维度汇总 + 评分概览
- `find_issues` — 查问题 + 微小第一步
- `get_report_section` — 查报告任意章节

**跨场工具（4个）**：
- `analyze_trend` — 跨场趋势 + 停滞检测
- `find_similar_past` — 语义搜索历史相似场景
- `find_patterns` — 反复出现的问题模式
- `read_theory` — 查阅 15 个学科理论

**对话管理**：滑动窗口（最近 8 轮）+ 老对话 LLM 压缩成摘要（非截断）

### 4.3 模块 2：人设工坊

**定位**：帮助主播找到、验证、迭代自己的人设定位。

**理念**：人设不是演出来的——是在你自然舒服的状态里长出来的。

**工具（4个）**：
- `diagnose_persona_style` — 从观众感知反向推导主播自然风格
- `compare_persona_fit` — 对比某种人设的标准行为 vs 实际行为，给匹配度评分
- `track_persona_consistency` — 追踪人设一致性趋势，识别容易偏离的场景
- `search_persona_examples` — 搜索某类型人设的历史成功案例（高分片段）

**对话铁律**：
1. 人设不是给定标准答案，是帮主播找到"自己想成为的"和"观众感知的"之间的平衡
2. 没有人设也没关系，风格稳定就够
3. 人设可以迭代，这不丢人
4. 永远不建议主播做自己不舒服的事

### 4.4 模块 3：刻意练习

**定位**：不止给建议，而是引导主播自己反思，建立练习节奏。

**理念**：好的教练不是给答案，是帮运动员自己找到答案。多用提问少用陈述。

**工具（4个）**：
- `generate_weekly_plan` — 基于焦点技能 + 主播经验等级，生成三场直播递进练习计划
- `reflection_guide` — 提出引导式反思问题（练的效果/遇到瓶颈/要不要换方向）
- `build_mental_representation` — 从主播自己历史中找最好表现，生成"做对了是什么感觉"自查清单
- `detect_practice_stagnation` — 检测技能是否陷入自动化停滞

**自动化停滞检测信号**：
1. 连续 4 场以上评分在 ±0.5 范围波动
2. 60% 以上 issue 项反复出现
3. 亮点列表缩短或重复
4. 改进建议内容高度重复

### 4.5 模块 4：话题引擎

**定位**：帮主播找到能聊的话题，减轻内容准备负担。

**理念**：数据源不是外部搜索，是主播自己的历史弹幕——观众已经告诉你他们想聊什么了。

**工具（4个）**：
- `extract_hot_topics_from_history` — 从最近弹幕和 ASR 提取观众关心的话题
- `match_topics_to_persona` — 把话题按主播风格适配成不同聊法
- `generate_content_calendar` — 一周话题日历（主题 + 展开路线 + 互动设计 + 转场语）
- `search_similar_chat_context` — 搜索历史上聊过某话题的片段

**话题来源优先级**：
1. 主播自己想聊的（热情所在）
2. 观众在弹幕里提过的（需求信号）
3. 主播风格适配的（不是所有热门话题都适合你）

## 五、跨场检索系统

### 5.1 技术选型：LanceDB

- **嵌入式**：零依赖，一个 pip install
- **列式存储**：分析查询天然列式
- **原生混合搜索**：SQL 过滤 + 向量搜索一条语句

### 5.2 三表设计

| 表名 | 向量字段 | 过滤字段 | 用途 |
|------|---------|---------|------|
| `session_summaries` | 场级摘要 | date, overall_score | 按时间+语义找相关场次 |
| `chunk_details` | 片段信息 | session_id, date, host_emotion | 找相似场景 |
| `issues` | 问题描述 | dimension, severity, priority | 找反复出现的问题 |

### 5.3 三步检索流程

```
Phase 1: 宽召回（LanceDB 语义搜索）
    query_emb = encode("3月 冷场 反复出现")
    candidates = search + WHERE date LIKE '03'
    → 返回 8 场相关复盘

Phase 2: LLM 重排
    给 8 场摘要发 LLM → 选出最相关的 3 场

Phase 3: 精准提取
    只加载这 3 场里与"冷场"相关的 issue 记录
    上下文从 ~75KB → ~5KB
```

### 5.4 Embedding 方案

用 LLM API 的 embedding endpoint（text-embedding-3-small），不装本地模型。
- 成本：~$0.00001/次
- 延迟：~200ms
- 打包体积：+0

## 七、后台任务模型

### 7.1 异步执行

流水线提交到后台线程执行，不阻塞 Electron 主进程和前端 UI。
用户可以在复盘跑着的时候看历史报告或写 Q&A 问题。

### 7.2 实时事件流

每个节点 emit 结构化事件：
```json
{"type": "event", "node": "analyze", "event": "analyze_done",
 "dimension": "互动效果", "chunk_id": 3, "score": 7.5, "latency_ms": 1200}
```

### 7.3 断点恢复

LangGraph checkpoint 持久化到 SQLite。Worker 崩溃重启后，从上次完成的节点继续，已调过的 LLM 不重复调用。

### 7.4 取消机制

用户可中途取消复盘，已完成的结果保留，未完成的维度可单独补跑。

## 八、质量保障环

```
每次 LLM 输出
    │
    ▼
Schema 校验（Pydantic）→ 格式不对 → Auto-fix retry（3 次）
    │
    ▼
自检岗哨（时间戳在范围内？数据来源存在？评分与评语一致？）
    │
    ▼
原始输出 + _meta（prompt 版本 / model / token 用量 / cost / 是否缓存）
    │
    ▼
不可变存储（v1 / v2 / v3，不覆盖历史版本）
```

### 费用透明

每场复盘产出费用摘要：
```json
{
```

## 十、部署方案

### 10.1 PyInstaller 打包

```bash
# 不再打包 prompts 目录！Worker 只含 Python + 依赖库，不含任何提示词文件
pyinstaller --onefile \
    --hidden-import=lancedb \
    --hidden-import=langgraph \
    growthplan_worker.py
```

产出：单个 `growthplan_worker.exe`，内嵌 Python + langgraph + lancedb。零提示词文件，零模型文件。

### 10.2 Electron 打包

```
growthplan-pc setup.exe
└── growthplan_worker.exe  ← extraResources（唯一需要额外打包的文件）
```

与改造前的区别：不再有 `resources/prompts/` 目录被打包。所有提示词内容由服务端分发。

### 10.3 后端服务

GrowthPlan 后端服务承担两个职责：

| 职责 | API | 说明 |
|------|-----|------|
| 收费验证 | POST /subscriptions/validate | 启动码验证，无效则拒绝进入应用 |
| 心跳保活 | POST /subscriptions/heartbeat | 定期心跳，检测持续在线 |
| 提示词分组 | GET /prompts/groups | 返回全部提示词组列表 |
| 提示词版本 | GET /prompts/groups/:id/versions | 返回某组的历史版本，客户端取最新 |
| 用户分组（可选） | user_id 参数 | 按用户返回不同版本 prompt，支持 A/B 测试 |

### 10.4 数据目录（仅用户数据，无提示词文件）

```
growthplan-pc/data/
├── vectors/                ← LanceDB 向量索引
│   ├── session_summaries.lance/
│   ├── chunk_details.lance/
│   └── issues.lance/
├── analysis_results/       ← 复盘结果（不可变版本存储）
│   ├── 20260614_abc123/

│   │   ├── v2_20260614T204500.json
│   │   └── latest.json
│   └── ...
└── growthplan_worker_state.db   ← LangGraph checkpoint 持久化
```

## 十一、使用场景

### 场景一：开播前 30 分钟 → 话题引擎

主播不知道今天聊什么 → 话题引擎从历史弹幕提取热词 → 按人设匹配聊法 → 生成一周话题日历。

这个完全可以做成实时的，而且这样做，效果并不好

### 场景二：直播中 → 后台静默

B站弹幕、礼物、SC 实时采集，音频实时录制。不打扰主播。

### 场景三：下播后 5 分钟 → 复盘流水线

点"开始复盘" → 费用预估确认 → 5-10 分钟产出 10 章节教练报告。包含评分概览、Sustain/Stop/Start、本周焦点 + 三阶脚手架、心理表征引导。
不用确认，费用，大概个范围就好，也不用10个章节的教练报告， 用户需要看的东西，要少，要精，   要考虑用户的程度

### 场景四：看报告有疑问 → 复盘问答

追问"为什么第三段评分低" → Agent 查具体片段各维度评分 → 结合历史找相似场景 → 给出改进建议 + 微小第一步。

这个其实也没必要，用户如果好奇的话，是可以去看具体每个片段的情况的
### 场景五：一周后 → 刻意练习

"我这周练的有进步吗？" → 对比近几场数据 → 反思引导（"你觉得哪次最满意？那次和不好的有什么不一样？"）→ 生成下周练习计划。
这个有一定必要

### 场景六：三个月后 → 成长轨迹

"我进步了吗？" → 各维度趋势 + 停滞检测 + 风格漂移感知 + 长期风险预警。

这个的话也不用做成agent
### 场景七：状态不好 → 底线保护

个人状态 < 3 → 报告唯一输出"建议休息" → Q&A 也不会给改进建议 → 系统的底线是主播的健康。
这个是本身设计的功能

## 十二、技术选型总览

| 层面 | 选型 | 原因 |
|------|------|------|
| 流水线编排 | LangGraph | 固定步骤 + 并行分支 + 条件重试 + checkpoint |
| 对话 Agent | LangGraph ReAct Agent | 开放式对话 + 按需工具调用 |
| 向量存储 | LanceDB（嵌入式） | 零运维，原生混合搜索（语义 + SQL 过滤） |
| Embedding | LLM API（text-embedding-3-small） | 不给桌面应用塞 PyTorch |
| 并发控制 | asyncio.Semaphore(max=8) | 防 API 限流 + 指数退避 |
| 结果缓存 | 内容哈希（SHA256） | 重跑不花钱 |
| 断点恢复 | LangGraph SqliteSaver | 关机重启不丢进度 |
| 前端通信 | stdin/stdout JSON | 和现有 Worker 协议一致 |
| 打包部署 | PyInstaller + Electron extraResources | 单 exe，零依赖 |
| LLM API | OpenAI 兼容接口 | 方便切换模型 |
| 提示词分发 | Electron IPC → Worker stdin，内存持有 | 不落盘，服务器统一管理，支持热更新 |

## 关键设计模式（从 Claude Code 借鉴）

1. **子 Agent 层级**：编排器不直接调 LLM，每个维度分析升级为有自主工具的子 Agent
2. **按角色授予工具**：每个 Agent 只看到它需要的 2-4 个工具，不会在 13 个工 具里选错
3. **Pre-flight 预估**：做事前先算账，跑流水线前弹出费用和调用次数确认
4. **后台 Agent 不阻塞**：长任务异步执行，用户可以切换页面
5. **对话压缩非截断**：老对话用 LLM 压缩成摘要保留关键信息
6. **自省循环**：关键节点完成后再发一次自检，防幻觉传播
7. **不可变操作日志**：每次分析结果独立版本，不覆盖历史
8. **Hooks 事件系统**：可配置的 `on_review_complete`、`on_score_below`、`on_stagnation_found` 钩子
9. **提示词零本地存储**：所有 prompt 由服务端分发，应用启动时通过 Electron IPC → Worker stdin 传递，Worker 全程只读内存中的 PromptStore。服务端同时承担收费和 prompt 管理，不可达则应用被许可验证拦截。
