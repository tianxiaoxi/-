## 零、核心隐喻

**软件不是代码堆叠，是一群人通过技术中介的协作系统。**

把软件当成一家公司来看——每一个模块是一个部门，每一条 API 是部门间的沟通机制，每一次用户操作是公司与客户的互动仪式。

这个映射让原本"纯技术"的软件架构问题，变成了"有人的社会系统"问题。而六道因果络和道一引擎的全部社会分析能力——仪式链、心之壁、18 条因果路径、五域归因——因此可以直接平移。

```
公司                   →  软件
────                   ──────
CEO / 架构师           →  核心架构层 / 技术负责人
部门                   →  领域模块 / 限界上下文
跨部门协作             →  模块间接口 / API 调用
部门墙 / 信息孤岛      →  模块耦合 / 紧绑定
人多了就拆部门         →  代码大了就拆模块
部门有 KPI             →  模块有职责边界
部门间扯皮             →  模块间循环依赖 / 接口爆炸
团队加班到 burnout     →  模块被过度膨胀到"上帝类"
```

## 一、四层组织模型

软件作为一个"公司"，天然存在四层组织。每层有自己的前台（对外呈现）和后台（内部状态），也有自己接触的"客户"。

```
 层次 0：客户组织
 ────────────────────────────────────────
  终端用户 / 调用方 / 下游系统
  "客户"——不是软件的一部分，但定义了软件存在的理由
 ────────────────────────────────────────
         │
         │ 接口 A：用着省力吗？
         │ 用户操作是否直觉？反馈是否及时？学习成本多高？
         ▼
 层次 1：前台组织（UI/UX/CLI/API 外观层）
 ────────────────────────────────────────
  用户直接打交道的一切——界面语言、交互动效、API 契约的开放性
  相当于公司的"销售部 + 客服部 + 前台接待"
  后台状态：设计一致性疲劳度、用户反馈堆积量、A/B 测试待办
 ────────────────────────────────────────
         │
         │ 接口 B：调用顺畅吗？
         │ 接口定义是否刚好完成一个业务语义？调用链多深？
         ▼
 层次 2：后台组织（业务逻辑 / 数据层）
 ────────────────────────────────────────
  用户看不到但业务依赖的一切——核心算法、数据库 schema、消息队列
  相当于公司的"产品研发部 + 财务部 + 仓储物流"
  后台状态：技术债务存量、测试覆盖率、领域模型与现实的偏移度
 ────────────────────────────────────────
         │
         │ 接口 C：运维省人吗？
         │ 部署成本？排障效率？配置标准化程度？
         ▼
 层次 3：运维组织（基础设施 / 开发运维层）
 ────────────────────────────────────────
  让软件持续运行的人——开发、SRE、DBA、安全
  相当于公司的"行政部 + IT 支持 + 物业"
  后台状态：on-call 压力、工程师倦怠度、人员流动率
 ────────────────────────────────────────
```

### 1.1 每层都是一个"社会角色"

按照道一 34 行引擎，每层可以建模成一个独立的 `Character`：

```
层_X_Character:
  pool: 0.65          # 该层的"合道度"——跟现实需求的匹配程度
  memories: [...]     # 该层经历过的关键事件（需求变更、用户投诉、架构决策）
  base_drain: 0.05    # 每轮自然消耗（运行成本）
  base_recovery: 0.02 # 每轮自然恢复（日常维护乐观产出）
```

不同层之间的交互通过**事件传播**实现——一个层的事件（如"新需求到达"）会成为另一层的 tick() 输入：

```
客户组织 → 前台组织的事件："用户反馈按钮太难找了"
  前台.tick(emb=[低效价, 高唤醒度, ...], intensity=0.6)
    → 前台.pool 下降（设计压力）
    → 前台.memories 追加（记住了这条反馈）
    → 传播给后台：前台把需求转成功能描述
      → 后台.tick(...)
        → 后台.pool 下降（实现压力）
        → 传播给运维：后台把功能交付给运维
          → 运维.tick(...)
            → 运维.pool 下降（部署成本）
```

## 二、每层的六道维度映射

每层的"健康度"（pool）可以拆成六道因果络的六个维度。但不同的层，六个维度的含义不同。

### 2.1 前台组织（层级 1）的六维度

| 维度 | 前台组织的语义 |
|------|-------------|
| **维度1·前台形象** | UI 设计语言的一致性、品牌调性、第一印象 |
| **维度2·互动效果** | 用户操作流畅度、反馈延迟、错误提示质量——**"用着舒服吗"** |
| **维度3·关系网络** | 用户社区活跃度、用户忠诚度、NPS、流失率 |
| **维度4·资源营收** | 广告收入 / 订阅收入 / 付费转化 / 获客成本 |
| **维度5·内部状态** | 设计团队的疲劳度、设计系统维护成本、交互规范完成度 |
| **维度6·产出质量** | UI 渲染性能、可访问性评分、设计还原度 |

### 2.2 后台组织（层级 2）的六维度

| 维度 | 后台组织的语义 |
|------|-------------|
| **维度1·前台形象** | API 文档质量、接口开放性、SDK 易用性 |
| **维度2·互动效果** | 跨模块调用损耗、内部 API 的语义完整性 |
| **维度3·关系网络** | 模块依赖图密度、循环依赖数、服务间耦合度 |
| **维度4·资源营收** | 人月投入分配、技术债务利息、基础设施成本 |
| **维度5·内部状态** | 代码可维护性、测试覆盖率、重构意愿、领域模型偏移度 |
| **维度6·产出质量** | Bug 率、性能指标（P99 延迟）、发布成功率 |

### 2.3 运维组织（层级 3）的六维度

| 维度 | 运维组织的语义 |
|------|-------------|
| **维度1·前台形象** | 运维文档质量、on-call 响应速度的对外承诺 |
| **维度2·互动效果** | 部署一键完成度、监控告警准确率、排障路径清晰度 |
| **维度3·关系网络** | 与开发团队协作紧密度、跨团队排障机制 |
| **维度4·资源营收** | 基础设施账单、运维人力成本、自动化节省 |
| **维度5·内部状态** | 工程师倦怠度、on-call 频率与睡眠质量、人员流失风险 |
| **维度6·产出质量** | 系统可用性（SLA/SLO）、MTTR、变更失败率 |

## 三、层间接口的"合道"判定

层与层之间的接口是整个框架最关键的部分。每层接触的是"不同的人"——合道意味着"我用这个接口省力"。

### 3.1 接口 A：客户组织 ↔ 前台组织

**接口载体**：UI 界面、API 文档、CLI 帮助文本、错误提示

**合道判据**——用户完成一个任务需要多少步认知决策：

```
合道（省力）          ←→  不合道（费力）
─────────────────────────────────────
用户自然走完流程        用户需要看文档才能操作
错误提示告诉你怎么办    错误提示给你一个 Code
操作可撤销              操作不可逆
学习成本为零            学一次才能用
反馈 < 100ms            反馈 > 1s
```

**池效应**：每次用户在合道的界面上完成一次任务 = 前台组织的 base_recovery +0.01。每次用户卡住或困惑 = 前台收到一个 drain 事件。

### 3.2 接口 B：前台组织 ↔ 后台组织

**接口载体**：REST API、GraphQL query、RPC、事件/消息

**合道判据**——一个前端操作需要几次后端调用：

```
合道（省力）          ←→  不合道（费力）
─────────────────────────────────────
一次请求完成一个业务语义   需要 N 次请求拼凑一个页面
接口名描述做什么           接口名描述数据结构
有版本管理                 版本在 URL 里乱写
错误码有语义层             错误码全是 500
字段刚好够用               字段要么太多要么太少
```

**池效应**：一次合道的接口调用 = 后台 pool 不变或微涨（因为自然恢复覆盖了微小消耗）。一次需要前端绕路的不合道调用 = 前台和后台各 drain 0.02（沟通损耗双方承担）。

### 3.3 接口 C：后台组织 ↔ 运维组织

**接口载体**：配置管理、部署脚本、监控仪表盘、日志格式

**合道判据**——一个运维操作需要多大的上下文：

```
合道（省人）          ←→  不合道（费人）
─────────────────────────────────────
部署 = 一个命令           部署 = 一本操作手册
日志统一格式              每个模块日志格式不同
监控大盘一秒看懂          需要翻 5 个页面拼出故障全貌
扩缩容自动化              扩缩容要改配置重启
配置中心化                配置散落在 N 个环境变量里
```

**池效应**：运维接口不合道的代价是**人力膨胀**——运维组织的 pool 持续下滑直到团队扛不住。这时软件公司会看到典型的"10 个人管 3 个服务"现象。

## 四、18 条因果路径的软件版

六道因果络的 18 条路径在"软件当公司"的映射下，每一条都有明确的现实对应。

### 4.1 经过互动枢纽的路径

| 编号 | 路径 | 软件语义 | 典型案例 |
|------|------|---------|---------|
| **①** | 形象↔互动 | UI 设计质量 ↔ 用户操作流畅度 | 设计改版后日活上升——好设计提升互动质量 |
| **①↺'** | 表演→自我认知偏移 | 团队长期对外说"系统稳定"→ 自己信了 → 忽视重构 | 管理层宣称"架构完美"→ 没人敢提技术债务 |
| **②** | 互动→关系 | 用得顺手 → 用户粘性增加 | 操作流畅 → 日活留存双涨 |
| **③** | 互动≈产出 | 用户操作质量 ≈ 模块交付质量 | CI 流水线顺畅 → 发布稳定性上升 |
| **④** | 互动→资源(交易型) | 交互体验好 → 付费转化率上升 | 一键下单比三步下单 GMV 高 30% |
| **⑤** | 互动→状态(消耗) | 大量用户反馈涌入 → 团队应对压力 → 倦怠 | 用户暴增 → 客服团队 burnout |

### 4.2 不经过互动枢纽的路径

| 编号 | 路径 | 软件语义 | 典型案例 |
|------|------|---------|---------|
| **②'** | 关系→资源(关系型) | 社区口碑 → 自然获客 | 开源社区的 star 数 → 企业采购咨询量 |
| **⑤'** | 关系→状态(缓冲) | 忠实用户的理解 → 缓解团队压力 | 老用户说"理解你们在重构"→ 团队心态稳住 |
| **⑥** | 状态→形象(崩塌) | 内部腐烂 → 一次大故障暴露 | 技术债务积累 → 数据泄露/大 outage → 用户信任崩塌 |
| **⑥'** | 资源↔状态 | 正螺旋：投入人力 → 代码变好 → 更多业务 → 再投入。负螺旋：裁员 → 交付崩 → 丢客户 → 再裁员 | |
| **⑦** | 产出→状态(认知负荷) | 频繁发布 → 技术债务积累 → 代码腐烂 | 每周三发版 → 半年后一碰就碎 |
| **⑦'** | 运营→状态(基线消耗) | 持续性运维负担 → 团队内部状态下滑 | on-call 轮换 → 工程师睡眠质量下降 → pool 缓慢下降 |

### 4.3 慢变量路径

| 编号 | 路径 | 软件语义 | 典型案例 |
|------|------|---------|---------|
| **⑧** | 关系→形象(塑形) | 用户期待 → UI 改版方向 | 用户说"太复杂了"→ 设计往极简走 |
| **⑨** | 形象→状态(维护成本) | 设计越精美 → 维护成本越高 | 复杂的交互动画 → 每次改版耗时翻倍 |
| **⑩** | 形象→产出(约束) | 设计规范限制功能边界 | 设计系统没有"批量操作"组件 → 批量功能要重新设计 |
| **⑪** | 产出→关系 | 新功能 → 用户增长或流失 | 上线 AI 复盘功能 → 老用户回流 |
| **⑫** | 关系→产出(共创) | 开源社区/用户贡献 → 功能迭代加速 | 用户提 PR → 半年完成一个小团队做一年的功能 |
| **⑬** | 资源→产出(投入) | 更多研发投入 → 更多功能产出 | 团队从 3 人扩到 10 人 → 迭代速度翻倍（短期线性，长期受康威定律约束） |

## 五、心之壁：前台-后台边界分析

心之壁是"软件公司"这个隐喻下最有解释力的概念。每个层都有前台（对外呈现）和后台（内部状态），两者之间的边界就是**心之壁**。

### 5.1 三层的心之壁

```
层次 1 前台组织
  ┌─────────────────────┐
  │ 前台呈现: UI/UX/API  │ ← 用户看得见的
  │─────────────────────│
  │  ═══ 心之壁 ═══     │ ← 设计团队的内部压力在这里
  │─────────────────────│
  │ 后台状态: 设计疲劳度  │ ← 用户看不见的
  └─────────────────────┘
         │  接口 B
         ▼
层次 2 后台组织
  ┌─────────────────────┐
  │ 前台呈现: API/DTO/    │ ← 前台组织（及下游）看得见的
  │         接口契约      │
  │─────────────────────│
  │  ═══ 心之壁 ═══     │ ← 技术债务、腐烂代码被藏在这里
  │─────────────────────│
  │ 后台状态: 代码健康度  │ ← 外人看不见的
  └─────────────────────┘
         │  接口 C
         ▼
层次 3 运维组织
  ┌─────────────────────┐
  │ 前台呈现: SLO/SLA/   │ ← 业务方看得见的
  │         可用性承诺    │
  │─────────────────────│
  │  ═══ 心之壁 ═══     │ ← on-call 压力被藏在这里
  │─────────────────────│
  │ 后台状态: 工程师倦怠度│ ← 外人看不见的
  └─────────────────────┘
```

### 5.2 心之壁厚度的判定标准

| 心之壁 | 特征 |
|--------|------|
| **薄壁** | Bug 直接弹给用户；error 信息含内部细节；加载转圈 > 3s；团队状态不好时用户能感受到（回复变慢、质量下降） |
| **中等壁** | 用户偶尔遇到小问题但可接受；团队有压力时表面还能撑一段时间（几周到几个月） |
| **厚壁** | 线上看起来一切正常，内部代码已腐烂到没人愿意动；UI 漂亮但背后是"屎山"；团队已经在 burnout 边缘但管理层不知道 |

### 5.3 ⑥ 路径：状态崩塌→前台暴露

软件行业最常见的崩塌模式：

```
阶段 1（潜伏）: 技术债务慢慢积累。每次"先上线再说"加 1%
阶段 2（感知）: 有个别老员工开始提"需要重构了"，但被业务优先级压住
阶段 3（临界）: pool 跌破 0.3。任何一次普通变更都可能触发连锁反应
阶段 4（崩塌）: ⚠ 一次发布翻车 / 数据泄露 / 性能雪崩 → 直接暴露给用户
```

**检测方法**：监控 "前台承诺 vs 后台实际" 的差值。承诺可用性 99.9% 但 on-call 每周被叫醒 3 次——差值 = 心之壁厚度。

### 5.4 ①↺' 路径：表演→自我认知偏移

技术团队长期对外说"一切正常"，自己都信了——这是软件行业最常见的心智陷阱。

信号：
- Team retro 上无人提及技术债务（因为"一直被压着没人提"）
- 新成员入职后发现"真实情况跟面试说的不一样"
- 架构文档很久没更新（因为"不重要"）
- manager 说的"系统稳定性"和实际 P50 延迟之间的差距越来越大

## 六、道一引擎的多角色扩展

现有的道一 34 行引擎（`Character` 类）只有**一个角色**。要推演"软件即公司"的因果网络，需要扩展为**多角色联动仿真**。

### 6.1 多角色引擎的核心结构

```python
class OrgCharacter:
    """组织角色——比单人 Character 多一个 '影响半径' 的概念"""
    def __init__(self, name: str, pool: float = 0.5, memories: list[dict] | None = None):
        self.name = name          # "前台" / "后台" / "运维"
        self.pool = pool
        self.memories = memories or []
        self.inbox: list[dict] = []   # 来自其他角色的事件队列

    def receive(self, from_name: str, event_emb: list[float], intensity: float,
                description: str = ""):
        """接收来自其他角色的事件，存入 inbox"""
        self.inbox.append({
            "from": from_name,
            "emb": event_emb,
            "intensity": intensity,
            "description": description,
        })

    def tick(self, base_drain=0.05, base_recovery=0.02, turn=0):
        """处理 inbox 中的所有事件 + 自然消耗/恢复"""
        total_drain = base_drain
        for event in self.inbox:
            drain = event["intensity"] * 0.3   # 每个入站事件带来消耗
            total_drain += drain
            # 事件写入记忆（如果强度够高）
            if event["intensity"] > 0.5:
                self.memories.append({
                    "emb": event["emb"],
                    "intensity": event["intensity"],
                    "turn": turn,
                    "description": f"[来自{event['from']}] {event['description']}",
                })
        self.inbox = []  # 清空 inbox
        self.pool = max(0.0, min(1.0, self.pool - total_drain + base_recovery))
        return self.pool


class OrgSimulator:
    """多角色组织仿真器"""
    def __init__(self):
        self.characters: dict[str, OrgCharacter] = {}
        self.turn = 0

    def add_character(self, name: str, pool: float = 0.5):
        self.characters[name] = OrgCharacter(name, pool)

    def send_event(self, from_name: str, to_name: str,
                   emb: list[float], intensity: float,
                   description: str = ""):
        """从 from_name 向 to_name 发送一个事件"""
        if to_name in self.characters:
            self.characters[to_name].receive(from_name, emb, intensity, description)

    def tick_all(self):
        """所有角色同时 tick 一轮"""
        self.turn += 1
        results = {}
        for name, char in self.characters.items():
            pool_new = char.tick(turn=self.turn)
            results[name] = round(pool_new, 4)
        return results
```

### 6.2 三层组织的事件流

```
客户事件                          → 前台.receive("客户", ...)
  (用户投诉、新需求、操作行为数据)
       ↓
前台.tick() 结束后                → 后台.receive("前台", ...)
  (前台把需求转成技术方案传给后台)
       ↓
后台.tick() 结束后                → 运维.receive("后台", ...)
  (后台把发布物传给运维)
       ↓
运维.tick() 结束
```

但实际软件中事件是**双向**的：

```
前台.receive("后台", emb=[低效价,唤醒度高], intensity=0.7, desc="后台接口返回结构变了，前端要改代码")
  → 前台.pool -= 0.7 * 0.3  # 前台被 drain

后台.receive("前台", emb=[中效价,中唤醒], intensity=0.4, desc="前台要求新增一个字段")
  → 后台.pool -= 0.4 * 0.3  # 后台被 drain

运维.receive("后台", emb=[高效价,唤醒度低], intensity=0.6, desc="后台新模块部署需要新基础设施")
  → 运维.pool -= 0.6 * 0.3  # 运维被 drain
```

## 七、推演模式：四种仿真

继承三生万物的三种模式，加一种"软件专属"模式。

### 7.1 模式 1：基线推演

"如果就这样一直开发下去，什么也不改，各层的健康度会怎么走？"

输入：
- 当前各层的初始 pool（由六道因果分析或架构评估得出）
- 当前各层的 memories（历史事件：上次重构、上次大 outage、关键人员离职）
- 自然消耗/恢复参数（由团队规模、发布节奏推算）

输出：
- 四层 pool 曲线并排展示
- 哪一层先跌破安全线（pool < 0.3）
- 触发场景信号：⑥ 路径何时触发？

### 7.2 模式 2：事件推演

"如果发生特定事件，情况会怎么走？"

典型事件注入：
- **用户增长 10 倍** → 前台 receive（高唤醒、高强度），逐层传播
- **核心人员离职** → 后台 receive（负效价、高唤醒），逐层传播
- **竞品上线类似功能** → 前台 receive（中效价、高唤醒）
- **基础设施成本翻倍** → 运维 receive，传播到后台

输出：
- 每条事件分支的 pool 曲线与基线对比
- 各个层的恢复时间差异——哪个层恢复最快？哪个层被拖垮？

### 7.3 模式 3：干预推演

"如果现在采取措施，哪个干预性价比最高？"

典型干预：
- **重构核心模块**：后台短期 drain 增加（重构成本），但长期 base_drain 下降
- **自动化运维**：运维短期 drain 增加（搭建自动化），但长期 base_drain 大幅下降
- **增加 QA 资源**：后台短期 pool 稳定（减少返工），但长期 base_drain 下降
- **UI 改版**：前台短期 drain 增加，但维度1/维度2 评分上升

输出：
- 干预 vs 基线的 pool 恢复轨迹对比
- 效果排名——哪个方案让目标层 pool 最快回到安全区间
- 性价比分析——"效果 / 代价"比率

### 7.4 模式 4：模块拆分裂变推演（软件专属）

"这个模块什么时候该拆？"

三生万物原生模式是"一个角色推演它的命运"。但软件组织的独特需求是——**组织会分裂**。

逻辑：
1. 基线推演中发现某个角色（如"后台"）的 pool 持续下滑
2. 检查下滑原因：是跨层接口不合道导致的 drain，还是角色内部职责过重？
3. 如果内部职责过重：触发分裂事件
4. 分裂后：

```
原"后台"角色
  ├── "业务逻辑域"（新角色，继承原 60% pool 和部分 memories）
  └── "数据域"（新角色，继承原 40% pool 和部分 memories）
```

5. 分裂后的各角色重新跑推演，看：
   - 新域间的接口是否更合道（drain 是否下降）
   - 是否出现了新的跨域耦合问题
   - 总体的"组织熵"是否降低了

**分裂触发条件**：
- 一个角色的 pool 连续多轮低于 0.3
- 该角色的 memories 中含有大量"不相关"的事件（事件 emb 向量在向量空间中离散度高）
- 一个角色的 inbox 中来自"自己内部不同职责"的事件冲突频繁

## 八、实践工作流

从零开始用这个方法论分析一个软件项目，建议走以下步骤。

### Step 1：确定组织分层

界定当前软件的"三层组织"分别对应什么：

```
项目：GrowthPlan ─ 虚拟主播复盘工具

前台组织 = growthplan-pc/ + growthplan-web/growthplan-admin/
    用户接触的所有 UI + API 前端
后台组织 = growthplan-web/growthplan-server/
    复盘分析引擎、用户数据管理、AI 分析逻辑
运维组织 = 部署脚本 + CI/CD + 基础设施
    Electron 构建、Spring Boot 部署、MySQL 管理
客户组织 = 虚拟主播 + 运营人员
    真正的终端用户
```

### Step 2：估算初始 pool

为每层的六个维度打分（1-10），加权聚合为初始 pool。

示例——后台组织：

| 维度 | 分数 | 依据 |
|------|------|------|
| 前台形象（API 质量） | 7 | OpenAPI 文档齐全，版本管理规范 |
| 互动效果（调用损耗） | 6 | 部分接口需要多次调用才能拼出完整信息 |
| 关系网络（耦合度） | 5 | 模块间有循环依赖迹象 |
| 资源营收（人月投入） | 6 | 小团队，资源紧张 |
| 内部状态（健康度） | 5 | 技术债务存在，测试覆盖不完整 |
| 产出质量（Bug率） | 7 | 整体稳定，偶有回归 Bug |

```
pool_后台 ≈ (7+6+5+6+5+7) / 60 = 0.60
```

### Step 3：建立初始 memories

列出每个组织记忆中的关键事件：

```yaml
前台.memories:
  - emb: [0.2, 0.8, 0.6, 0.5, 0.7]  # 负效价、高唤醒、高社会权重
    intensity: 0.7
    description: "用户反馈复盘报告加载太慢"
  - emb: [0.8, 0.6, 0.7, 0.3, 0.5]  # 正效价、中唤醒
    intensity: 0.5
    description: "AI 复盘功能上线后用户正面反馈增多"

后台.memories:
  - emb: [0.3, 0.7, 0.8, 0.6, 0.6]  # 负效价
    intensity: 0.8
    description: "一次数据迁移导致线上报告丢失"
  - emb: [0.7, 0.4, 0.5, 0.3, 0.4]  # 正效价
    intensity: 0.5
    description: "重构分析引擎后处理速度提升 3 倍"
```

### Step 4：运行基线推演

取 N=20 轮（模拟 20 个开发周期/冲刺），观察 pool 走势。

关键观察：
- 哪一层最先接近危险线（pool < 0.3）？
- 各层之间的 pool 差值在扩大还是缩小？（差扩大 = 心之壁变厚）
- 有没有出现典型路径信号？（如 ⑥ pool 下滑但前台表现稳定 = 厚壁假性平板）

### Step 5：基于路径信号提出干预

从基线推演的路径激活状态出发，提出 2-3 个干预方案。

```
干预 A：重构后台核心模块
  短期（T1-T3）：后台 pool 下降 0.1（重构成本），前台不受影响
  中期（T4-T8）：后台 base_recovery 从 0.02 → 0.04
  长期（T9+）：后台 pool 稳定在 0.55+，前台因为接口更稳定也受益

干预 B：增加前台自动化测试
  短期：前台 pool 下降 0.05
  中期：前台 base_drain 从 0.05 → 0.03（减少回归 Bug 的修复成本）
  长期：前台稳定，后台因减少被"Bug 回流"而间接受益
```

### Step 6：综合判断

综合基线 + 事件 + 干预三条线的对比输出最终推荐。

## 九、与传统建模方法的定位对比

| 方法 | 问的问题 | 回答的领域 |
|------|---------|-----------|
| **C4** | 系统有哪些容器？组件怎么连？ | 静态结构 |
| **DDD** | 领域边界在哪？聚合怎么划分？ | 业务逻辑建模 |
| **ATAM** | 架构能否满足质量属性？ | 架构决策评估 |
| **ADR** | 为什么选了 A 而非 B？ | 决策记录 |
| **软件组织建模法（本文）** | **各层之间的因果动力能撑多久？哪个接口最不合道？** | **演化趋势与组织健康** |

这个框架**不替代**C4 和 DDD，它回答的是前者不回答的问题：

> 这套架构划分方式，在时间推移下，**各部分的健康度会怎么变化**？当前看似合理的模块边界，**半年后会不会成为通信瓶颈**？什么时候该**主动重构**而不等到崩塌？

## 十、当前的局限与扩展方向

### 已知局限

1. **多角色引擎尚未实现**：目前道一引擎是单角色。`OrgSimulator` 是一个概念设计，需要正式实现为 Python 代码才能运行真实推演。

2. **emb 编码体系待定**：单人 34 行引擎用 5 维向量（效价、唤醒度、社会权重、自主威胁、新颖度）。多角色的"组织事件"是否需要新的编码维度尚未确定。

3. **初始 pool 估值的主观性**：当前依赖六维度打分加权。评分标准的校准需要跨项目数据积累。

### 扩展方向

- **康威定律集成**：组织沟通结构会镜像到软件架构。可以建模为"公司的人数/部门划分" → "模块依赖图的同构映射"。

- **Brooks 定律推演**：加人人手不一定加快交付。可以建模为"新增人手 → 短期培训成本（drain）→ 中期产出增加（recovery 上升）→ 长期沟通复杂度上升（base_drain 上升）"的推演。

- **组织熵监控**：多角色系统的总熵 = sum(各角色 pool 方差) + sum(跨层事件延迟方差)。熵持续上升 = 系统在走向无序。

## 十一、AI 时代的轻量级闭环

这个框架不是要增加开发负担，而是刚好相反——在 AI 写代码的当下，它可以轻到几乎"顺手"。

### 11.1 日常开发：AI + 框架 = 顺手合道

在 Cursor 等 AI 编码环境中，把框架作为上下文规则注册进去（如 `.cursor/rules/` 下的 `.mdc` 文件）。AI 生成代码时会自动参考——

- 新代码如果增加跨层调用次数，AI 会倾向于更耦合低的方案
- 心之壁厚的模块（pool 已经低的）先不动，新功能优先加新模块
- 涉及运维负担大幅增加的变更会标红

**不需要额外步骤**。写代码的过程本身，AI 就在这个框架的意识里工作。

### 11.2 有疑虑时：跑一趟模拟

开发过程中遇到判断不了的情况——"这个改动到底会不会把后台拖进去？"——就跑一趟模拟。

不需要跑真实的 tick 循环。直接让 AI 用框架的视角评估：

> *"这个改动对前台 pool 的影响约 -0.01，对后台约 -0.04，对运维约 -0.02。激活了路径 ⑦（产出→状态认知负荷），因为频率升高会积累技术债务。但整体净收益为正，建议实施，注意一个月后检查后台 pool。"*

这就是**非正式模拟**——人工标注 + 框架分析，不需要运行 `OrgSimulator` Python 代码。在 OrgSimulator 正式实现之前，也能用。

### 11.3 上线前：应急演练

### 11.4 完整闭环

```
日常写代码 ──▶ AI 带着框架写，顺手合道
      │
      │ 有疑虑
      ▼
跑一趟模拟 ──▶ 看 pool 走不走偏
      │
      │ 上线前
      ▼
应急演练 ──▶ 注高压事件看哪层先崩
      │

上线
```

**整个闭环不需要任何重流程，在 AI 时代这个成本接近于零。**

## 十二、应急演练——在事故之前确认承受力

突发事故无法预测（这是原则，第六章已说明）。但**事故的强度可以预设**——应急演练不回答"会不会出事"，而是回答**"如果出了这么大的事，系统能不能撑住"**。

### 12.1 演练模式

基于三生万物的模式 2（事件推演），注入高强度事件到仿真器：

```yaml
演练场景: 数据库主库故障
  注入事件:
    from: "运维"
    to: "后台"
    intensity: 0.9
    description: "主库不可用，需要切从库"
```

跑推演后观察：

```
注入前状态:
  前台 pool = 0.65
  后台 pool = 0.50
  运维 pool = 0.55

注入后 T+3 轮:
  前台 pool = 0.58  （用户看到 502，但界面在降级后恢复）
  后台 pool = 0.22 ⚠（切换从库过程中队列积压）
  运维 pool = 0.15 ‼（全员 on-call 上线抢）

结论: 运维层先崩。切换流程不是自动化的，依赖人工操作。
      下一步: 将主从切换自动化，降低运维层 drain。
      演练后运维 pool 恢复目标: 0.15 → 0.40（同样强度的事故下）
```

### 12.2 标准演练清单

| 演练场景 | 注入事件 | 关注层 | 预期推演 |
|---------|---------|--------|---------|
| **流量洪峰** | 用户量 × 10 | 前台、后台 | 看哪层先扛不住 |
| **数据库主库故障** | DB 不可用，intensity 0.9 | 后台、运维 | 切换链路是否自动化 |
| **核心人员离职** | 后台 memories 清零，intensity 0.8 | 后台 | 知识保留度、文档完备度 |
| **基础设施成本翻倍** | 运维 drain 加倍 | 运维 | 成本弹性、冗余砍单速度 |
| **竞品上线** | 前台 receive 负效价事件，intensity 0.7 | 前台 | 用户流失路径、差异化壁垒 |
| **安全漏洞曝光** | 前台 receive 紧急事件，intensity 0.95 | 全部三层 | 响应链路、用户信任恢复 |

### 12.3 演练的价值不在"预测"

应急演练的核心价值不是预测到具体哪次事故，而是——

1. **发现盲区**：跑一趟演练就能看到"我们从来没想过切换从库要 20 分钟"
2. **验证恢复链**：自动化链路有没有实际覆盖到关键路径？
3. **校准容忍度**：当前架构下，用户量涨到多少时系统不再是"可靠"的？

> 后记  
> 这个框架起源于一个追问："六道因果络能不能分析软件架构？"  
> 答案不是"能"或"不能"，而是——**如果你把软件当成一家公司来看，就能。**  
> 因为软件不是一个技术系统，它是一群人通过代码的协作。而道一引擎的语言——pool、memories、tick、drain、recovery——本身就是描述"有心之物如何消耗与恢复"的语言。  
> 软件有心。只是以前没人这么看它。  
> 这个框架的价值不在精密度，而在**顺手**——AI 时代下，合道不需要额外成本。日常写代码带着框架走，有疑虑跑一趟模拟，上线前做一轮应急演练。轻到近乎免费。
