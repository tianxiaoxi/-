## 二、当前架构的三个根本矛盾

### 矛盾一：设计说"渐进式披露"，但每一句话都在违反

系统设计文档里写了：

> 每个 LLM 请求只收 60-80 行指令

但实际：

| 文件 | 行数 | 相当于 |
|------|------|--------|
| `02_互动效果分析.txt` | **767 行** | 10× 设计目标 |
| `07_人设定位分析.txt` | **908 行** | 11× 设计目标 |
| `13_综合总结.txt` | **313 行** | 4× 设计目标 |

一个 767 行的 system prompt 里嵌入了角色设定、全部理论框架、全部子维度判断表、全部评分标准、全部 JSON schema。LLM 的注意力窗口是有限的——你把所有东西都塞进去了，它就**所有东西都不认真看**。

根本问题：**渐进式披露被设计了但从没被真正执行**。框架层/评分层/理论层的三层分离写在设计文档里，但 02~07 的每个分片分析文件都把所有层糅合在一个大文件里，LLM 收到的是一个"包含了全宇宙"的 prompt。

---

### 矛盾二：系统是"分析机"而不是"教练系统"

整个 pipeline 的核心产出是什么？一份 JSON 报告。里面有评分、P0/P1/P2、severity、confidence、sub_scores。

你去看任何一个真正的好教练——不管是体育教练、表演教练还是心理咨询师——他们从来不给你一个"评分表"。他们会说：

> "你今天有一件事做得特别对，也有一件事可以试试换种方式。想先听哪个？"

你现在系统的出口是一份**成绩单**（report card），不是一个**教练对话**（coaching intervention）。这和约束 12 里写的哲学——"语气如教练，不如老师；如朋友，不如家长"——是冲突的。成绩单天然就是"老师/家长"的语气结构，不管你用多温柔的词去填它。

---

### 矛盾三：维度 Agent 完全隔离，但问题是跨维度的

一个真实的例子：

> 主播在某段时个人状态很差（06 维度），导致互动冷场（02 维度），互动冷场导致礼物减少（04 维度）。

当前架构下：
- Agent 06 看到"状态低分"，标记一个 issue
- Agent 02 看到"互动低分"，标记另一个 issue
- Agent 04 看到"营收低分"，标记第三个 issue
- 它们**永远不会对话**，永远不会说"状态差→互动差→营收差是因果链，不是三个独立问题"

Step 3 的维度汇总是**聚合**（aggregation），不是**交叉推理**（cross-reasoning）。它只是在每个维度内部说"这个维度总体怎么样"，而不是说"这些维度之间有什么关系"。

Step 4 的综合总结收到 6 份汇总报告，让一个 LLM 在一次性调用中做跨维度因果推理——这是典型的"把所有认知负荷堆到最后一步"的模式。

## 改动 1：把"渐进式披露"从设计文档搬进 prompt 执行层

**问题**：设计说三层分离（framework → scoring → theory），但 02~07 的每个文件把三层糅在一起。

**方案**：不是"把 prompt 文件拆成小文件"（这太浅了），而是**让每个 LLM 调用只带和它任务直接相关的上下文**。

### 具体做法

```
不是：
  system_prompt = "你是互动效果分析顾问，你会获得以下理论、评分标准和...
                   以下是互动仪式链理论（Collins）的详细描述（200行）...
                   以下是社会交换理论（Thibaut & Kelley）的详细描述（150行）...
                   以下是评分标准（100行）...
                   以下是输出 JSON schema（80行）...
                   现在开始分析这个片段。"

而是用 4 轮渐进式调用：
```

#### Round 1: Observe（观察）

```
system_prompt: "你是一个虚拟主播互动观察员。你的任务只有一件：
               识别这段时间里主播和观众之间实际发生了什么。
               不要评分，不要给建议，不要引用理论。
               输出：时间线叙事 + 关键互动事件列表。"
```

#### Round 2: Score（评分，仅在 Round 1 产出"有值得分析的事件"时执行）

```
system_prompt: "你是一个互动质量评估员。基于上一轮的观察，
               给这个片段打分。只打分，不给建议。
               评分时参考以下标准：[60行评分细则]
               输出：评分 + 评分依据。"
```

#### Round 3: Diagnose（诊断，仅在 Round 2 评分 ≤ 7 时执行）

```
system_prompt: "你是一个互动问题诊断员。基于前两轮结果，
               找出这个片段中互动问题背后的原因。
               可以查阅以下理论：[理论文件按需加载]
               输出：诊断 + 理论依据。"
```

#### Round 4: Advise（建议，仅在 Round 3 产出了诊断时执行）

```
system_prompt: "你是一个教练。基于前三轮结果，
               给出一个具体的、可执行的改进建议。
               只给一条建议。给主播能照着做的话术。"
```

### 为什么这一层是根本性的

这是真正意义上的"渐进式"——不是"文件分成三层"（那是静态拆分），而是**调用链上的逐步深入**（这是动态披露）。每一轮 LLM 的上下文窗口里只有它当前任务需要的信息。

关键机制：
- Round 2+3+4 是**条件执行**，不是必执行——如果 Round 1 发现没有值得分析的事件（如纯唱歌片段），后续轮次全部跳过
- Round 3 的理论文件是**按需加载**，不是在 system prompt 里预埋——只有诊断环节需要理论时才查阅
- 每一轮都以前一轮的输出作为上下文基础，但不是堆叠——LLM 看到的是"前一轮的结论摘要 + 本轮的判断指令"

### Round 3 理论按需加载的决策机制

采用"维度→理论"静态映射 + 精要版默认加载的两层策略：

**1. 基础映射表（领域专家预配置）：**

每个维度与 1-2 个核心理论的绑定关系由领域专家预先配置，例如：
- 互动效果 → 互动仪式链（Collins）+ 社会交换理论（Thibaut & Kelley）
- 人设定位 → 角色理论（Goffman）+ 叙事身份理论
- 个人状态 → 自我决定理论（Deci & Ryan）+ 情绪劳动理论

**2. 每个理论提供两个版本：**
- **精要版**（40-60 行）：包含该理论在主播复盘场景下的 3-5 个核心概念和判断信号，默认在 Round 3 加载
- **完整版**（200+ 行）：包含理论全貌，仅当 Round 2 的评分依据中标注"现象与已有理论框架不完全匹配"或诊断员主动请求时加载

**3. 加载流程：**
- Round 2 输出评分依据时，附带一个 `recommended_theories` 标签（取自映射表，可选 0-2 个）
- Round 3 默认加载映射表中的精要版；若评分依据标注了"理论与现象不完全匹配"，则在 prompt 中追加完整版内容的引用指令
- 多个理论精要版叠加后仍控制在 100 行以内，满足每轮 prompt ≤ 100 行的约束

## 改动 2：增加一个"跨维度推理层"

**插入位置**：当前 Step 3（维度汇总）和 Step 4（综合总结）之间。

**为什么**：当前 Step 4 承受了全部跨维度推理的认知负荷，但 Step 4 能调用多少次？只有 1 次。

### 新增：Step 3.5 Cross-Dimension Inference

```
Step 3.5: 跨维度推理节点

输入：6 份维度汇总（不扔全部，只扔每个维度的问题列表 + 评分时间线）
任务：
  1. 因果链检测：
     - 哪个维度的问题可能是"因"，哪个是"果"？
     - 例：60分钟的互动掉分→75分钟的营收掉分→因果链确认
     - 例：全场个人状态持续低→所有维度评分偏低→因果关系
     - 输出：因果链路图（dimension_A → dimension_B → dimension_C）

  2. 矛盾信号检测：
     - 两个维度的评分方向相反时（如互动好但营收差）
     - 这本身就是重要的发现——不是所有矛盾都需要修正
     - 输出：矛盾信号列表 + 解释假设

  3. 核心驱动维度识别：
     - 本场哪个维度是"牵一发而动全身"的？
     - 这可能不是"评分最低"的维度
     - 输出：核心驱动维度 + 为什么

输出：因果图 + 矛盾信号 + 核心驱动维度 + 解除冲突后的统一叙事
```

### 因果链检测的降级策略

LLM 的因果推理有已知的能力边界——它倾向于将时序相关性与因果关系混淆，也可能出现共因混淆（common cause confounding，如主播身体不适同时导致互动差和营收下滑，但 LLM 可能错误输出"互动差→营收差"）。因此 Step 3.5 的因果链检测需要内置容错机制：

**1. 因果链置信度标注：**
每条因果链输出附带一个 0-1 的置信度，并标注判断依据：
- 时序先后（A 的掉分发生在 B 之前）
- 内容相关性（A 的问题内容和 B 的问题内容有逻辑关联）
- 排除竞争假说（是否考虑了"第三个因素同时导致 A 和 B"的可能性）
- 跨场一致性（该因果模式是否在多场直播中复现）

**2. 置信度阈值与降级规则：**
- 置信度 ≥ 0.8 → 确认因果链，参与优先级升降档
- 置信度 0.5-0.8 → 标记为"可能关联"（关联链），在 Step 4 中呈现为"值得注意的模式"，但不作为优先级升降档的依据
- 置信度 < 0.5 → 不输出因果链，降级为"共变观察"（"维度 A 和 B 本场均偏低，但因果关系不明确"）

**3. 无法确定因果方向时的处理：**
当 LLM 无法确定因果方向（如两个维度同步下跌），输出标记为 `causal_direction: "undetermined"`（共变关系），放入"共变观察"列表，不参与优先级调整。Step 4 在教练语言中表述为"这两个维度都出现了波动——可能有关联，但这次我不确定哪个是根"。

### 矛盾信号的后续处理策略

矛盾信号（如互动好但营收差）在教练输出中按以下方式呈现：

**在教练干预包中：**矛盾信号作为 Pattern 要素的可选子项——"有意思的是，你的互动评分提升了，但营收反而降了。这种情况本身就是一个发现：说明你互动的质量和礼物转化之间还有一个环节没打通。"

**在教练对话中：**矛盾信号作为引导式提问的素材——"我注意到了一个有点矛盾的情况——你的互动比上周好了，但礼物反而少了。你直播时有感觉到观众的态度和付费意愿不太同步吗？"

**在扩展阅读层中：**矛盾信号归入"值得注意的信号"卡片（默认折叠），附带简短的可能解释（如"互动好但营收差 → 观众参与度高但付费意愿低，可能是礼物引导话术的问题"）。

矛盾信号默认不在首屏展示（避免困惑），但保留在扩展阅读和对话素材中供主播主动探索。

### 为什么这么设计

Step 4（综合总结）收到的不是 6 份孤立的报告，而是一份**已经做过交叉推理的整合分析**。Step 4 的 LLM 不再需要自己做"这个和那个有关系吗"的判断——这些判断已经在 Step 3.5 里做好了，Step 4 只需要把它们翻译成教练语言。

认知负荷分配：
- Step 3.5：逻辑推理（"这些维度之间有什么关系？"）
- Step 4：语言转化（"用主播听得懂的话说出来"）

两个任务需要不同的"思维模式"，应该由不同的 LLM 调用来承担。

## 改动 3：从"成绩单"模式切换到"教练对话"模式

**问题**：综合总结的结构是：

```
评分概览 → Sustain/Stop/Start → 本期焦点 → 可先放放 → 人设与风格 → 状态提醒 → 节奏总结
```

这是一个 **checklist for the AI to fill out**，不是一个 **coaching experience for the streamer**。

### 新方案：教练干预包（Coaching Intervention Package）

```
教练干预包不是一份报告，而是一个"对话启动包"：

1. 锚点（Anchor）：一句主播自己能感受到的话
   "今天直播第三段的时候，弹幕突然少了——你当时注意到了吗？"
   不是 AI 的评判，而是帮主播连接自己的体验

2. 模式（Pattern）：一个主播可能没有意识到的重复行为
   "这和你上周四第二段的状况很像——都是聊到自己不确定的话题时容易冷场。"

3. 焦点（Focus）：一个本期可以练习的具体技能
   "这周试试：每次觉得'这个话题可能有点冷'的时候，用一个选择题开场。"

4. 第一步（First Step）：30秒内可以做的事
   "明天开播前，准备三个'二选一'的问题写在便签上放屏幕旁边。"

5. 验证信号（Verification Signal）：主播怎么知道自己做对了
   "如果你抛出选择题后 10 秒内有 5 个人扣了 1，就说明你做对了。"

6. 休息提醒（Wellness Check）：仅在个人状态得分偏低时出现
   "这周如果太累了，休息一天不是偷懒。你的状态好了，聊天才会好。"

7. 扩展阅读（On-Demand）：可展开的深度分析
   "如果你想看具体每个时间段的详细分析，点这里。"
   默认折叠，用户主动点开才展示
```

### 关键区别

| 成绩单模式 | 教练干预包 |
|-----------|-----------|
| AI 提供一个"完整"的评价 → 主播被动接受 | AI 提供一个"有关联"的洞察 → 主播主动连接自己的体验 |
| 预设固定的输出结构 | 每次的输出结构由"这场最重要的发现"决定 |
| "你好/一般/较差"的评价标签 | 只告诉主播"哪里可以有变化" |
| 主播的感受是"被评估" | 主播的感受是"被理解、被支持" |

### 实现要点

报告章节（评分概览、Sustain/Stop/Start 等）不是删除——它们变成**扩展阅读层**的内容。默认给主播看到的是教练干预包（5-7 条简洁信息），如果主播想看细节，主动展开才看到完整报告。

**扩展阅读层的交互设计：**

扩展阅读层采用两层卡片结构，默认全部折叠：

1. **第一层：本场关键数据摘要**（1 张卡片）
   - 各维度分数一览（雷达图或横向条形图）
   - 因果链概要（一句话总结："本场互动冷场 → 导致营收下滑"）
   - 与上场对比的变化箭头（↑/↓/→）

2. **第二层：按维度的详细分析**（每个维度一张折叠卡片）
   - 卡片标题：维度名 + 一句话概要（如"互动效果 · 第 2、4 段有冷场信号"）
   - 展开后内容：当前版本综合总结中对应章节的内容（时间线、关键事件、评分依据）
   - 卡片顺序：按"本期焦点维度 → 其他深度维度 → 浅度维度 → 跳过维度"排列

前端交互：教练干预包底部有一个"📊 查看详细数据"入口，点击后展开扩展阅读层的卡片列表。主播可以逐张展开感兴趣的维度卡片。

## 改动 4：动态维度激活（Dynamic Dimension Activation）

**问题**：每场直播，不管内容是什么，6 个维度全部深度分析。一个主播如果连续 10 场营收都好，为什么每场还要深度分析营收？

### 新增：Step 0 - Triage

```
Step 0: Triage（1 次 LLM 调用，位于分片之前）

输入：整场直播的汇总统计（总时长、总弹幕量、总礼物价值、主播ASR情绪摘要）
       + 主播历史基线（最近 5 场的各维度平均分+标准差）
任务：
  1. 快速扫描：有没有维度明显不需要深度分析？
     判断标准：
     - 本场礼物总量 vs 主播历史基线：在基线 ±1 SD 以内 → 营收维度做浅度扫描
     - 本场弹幕总量 + 弹幕情绪极性：在健康范围内 → 互动维度做浅度扫描
     - 上一场某个维度有 P0 标记 → 本场该维度强制深度

  2. 输出：维度激活矩阵
     {
       "互动效果": "深度",
       "粉丝关系": "深度",   ← 上一场有粉丝流失信号，继续深度
       "流水营收": "浅度",   ← 连续 4 场稳定，扫一眼就行
       "内容质量": "深度",
       "个人状态": "深度",   ← 上一场已经偏低，必须深度
       "人设定位": "浅度"    ← 最近没什么变化
     }
```

### 三个激活级别

| 级别 | LLM 调用 | Prompt 大小 | 做什么 |
|------|---------|-------------|--------|
| **跳过** | 0 次 | — | 历史 5 场评分稳定（波动 <1 分），本场无明显异常，不分析 |
| **浅度扫描** | 1 次 | ~100 行 | 只判断"有没有明显问题"，不产出子维度评分，不产出详细 issue |
| **深度分析** | 4 轮 | 渐进式 | 完整的 Observe → Score → Diagnose → Advise 链 |

### 效果

一场"正常"的直播可能只有 2-3 个维度做深度分析，而不是 6 个全部深度。节省的 token 和注意力可以投入到真正需要深挖的维度——这意味着深度维度的分析质量会比现在更好（因为 LLM 不用同时应付 6 个维度的上下文）。

**底线保护**：个人状态维度不做浅度/跳过——除非连续 10 场评分 ≥ 8 且波动 < 0.5，否则始终"深度"。主播的健康不是可以跳过的事。

### 新主播冷启动策略

Triage 的激活判断依赖历史基线（最近 5 场的各维度平均分+标准差），但首次使用系统的主播没有基线数据。冷启动期的规则如下：

**1. 冷启动期定义：**主播的前 5 场直播为冷启动期。此期间不执行 Triage，全部 6 个维度强制深度分析——目的是积累基线数据，而非节省成本。

**2. 基线置信度字段：**Triage 的输出中增加 `baseline_confidence` 字段：
- `baseline_confidence: "established"`（≥ 5 场基线）→ 正常执行 Triage 激活判断
- `baseline_confidence: "accumulating"`（3-4 场）→ 执行 Triage 但仅做保守判断（只允许"深度→浅度"降级，不允许"深度→跳过"）
- `baseline_confidence: "insufficient"`（< 3 场）→ 跳过 Triage，全部维度强制深度

**3. 冷启动结束：**当累计 5 场全维度深度分析后，Step 6（跨场趋势存档）自动标记"基线已建立"，下一场自动启用完整的 Triage 激活逻辑。

### 全维度跳过时的边界行为

底线保护机制已将全维度跳过的概率降到极低（需要连续 10 场个人状态 ≥ 8 分 + 其余 5 个维度也都稳定在基线内），但当此情况发生时，系统行为定义为：

- Step 2 不发起任何 LLM 调用
- Step 4 输出一个极简版教练干预包，仅包含：**正向确认**（"本场所有维度持续稳定，暂无特别关注项。保持当前节奏。"）+ **扩展阅读入口**（"如果想回顾某个维度的历史趋势，点这里"）
- Step 5 教练对话入口正常开放（主播仍可主动发起对话讨论往期问题）

## 改动 5：用"因果链优先级"替代"评分优先级"

**问题**：当前的问题排序逻辑是：

```
P0（立即改）：评分 < 5 分的原因
P1（下次改）：明显提升互动效果的问题
P2（本月改）：长期优化项
```

这是**严重度排序**，不是**杠杆效应排序**。

一个 8 分的互动问题和 3 分营收问题同时存在时，P0 会指向营收。但如果互动问题才是"因"、营收问题是"果"呢？改互动，营收自然回升。改营收（比如更用力要礼物），反而可能让互动进一步恶化。

### 新方案：因果链驱动的优先级

```
问题排序逻辑变更：

旧逻辑（严重度驱动）：
  评分越低 → 优先级越高 → 出现在教练报告最前面

新逻辑（杠杆效应驱动）：
  1. Step 3.5 先用因果链检测找出"因"维度
  2. "因"维度里的问题优先级自动提升一档
     - 原 P1 → P0
     - 原 P2 → P1
  3. "果"维度里的问题优先级自动降低一档
     - 原 P0 → P1
     - 原 P1 → P2
  4. 如果"因"维度的评分不是最低的 → 教练提示里标注：
     "你营收掉到 3 分了——但根子在互动冷场上。
      这周练互动，营收会自然回来。"
  5. 如果存在独立问题（不受任何因果链影响）→ 保持原优先级
  6. 优先级冲突解决规则：
     - 链中节点自然处理：在因果链 A→B→C 中，B 既是 A 的"果"又是 C 的"因"，
       升降档效果恰好相抵，维持原优先级
     - 多链汇聚时取上限：多个因果链指向同一维度时，取所有链中优先级最高
       的那条结果（"优先响应最大的因果信号"）
     - 优先级至多升降一档：避免链式传播导致所有问题都是最高级
     - 升降冲突时优先升级：当同一维度从链 A 收到降级信号、从链 B 收到升级
       信号时，取升级（宁可多关注，不可漏掉）
  7. 在 Step 4 教练输出中标注"该维度优先级受因果链调整"，保持透明度
```

### 教练报告中的呈现

不做 `P0 / P1 / P2` 标签（那是"成绩单思维"），改为：

```
本期焦点（一个）：
  "互动冷场 → 导致营收下滑"。
  这周练互动。营收是自然结果，不是练习目标。

可以先放放：
  "人设定位有些模糊"。
  这个问题是真的，但不是本周的紧急事件。互动恢复后，人设问题会更清晰。
```

## 改动 6：用"结构化推理链"替代"JSON Schema"

**问题**：当前所有输出必须符合严格 JSON schema，Pydantic 校验失败 → auto-fix retry。这意味着：

- LLM 花 tokens 在格式化上，而非洞察上
- 格式正确但内容空洞的输出可能被接受
- auto-fix retry 消耗额外的 token 成本
- LLM 的思维是线性的（chain of thought），在嵌套 JSON 中强行打断

### 新方案：推理链格式（仅中间步骤）

```
不是 JSON：
  {
    "score": 7.5,
    "confidence": "high",
    "sub_scores": {"弹幕互动质量": 7, "杂谈力表现": 8, "情绪价值输出": 7, "控场能力": 8},
    "strengths": ["提问有章法", "回应及时"],
    "issues": [{"severity": "轻度", "confidence": "high", "timestamp": 120.0,
                "event": "主播连读8条弹幕未展开", "problem": "只回应不延伸",
                "discipline_analysis": "从互动仪式链看...",
                "better_practice": "选一条最有故事的展开",
                "change_difficulty": "中", "change_impact": "中"}],
    "suggestions": ["练习选弹幕的眼力"]
  }

而是推理链：
  ```
  OBSERVATION:
  在 00:12:30 - 00:15:00 期间，主播连续念了 8 条弹幕但没有在任何一条上展开。
  弹幕从第 2 分钟开始从"讨论"变成"单向报到"（"来了""打卡"占比从 15% 升到 40%）。
  这是"假热闹"信号。

  SCORE: 互动质量 6/10

  WHY: 减分不是因为主播没互动——她读了弹幕。减分是因为互动停留在"回应"层，
  没有进入"延伸"层。弹幕有来，但没回。

  ROOT_CAUSE: 这 8 条弹幕的内容彼此不相关（从"吃什么"跳到"打游戏"跳到"今天天气"），
  主播试图照顾每一条但没能串成一条线。

  SUGGEST: 下次遇到多条不相关弹幕时，选一条最有"故事性"的展开，
  其他弹幕用一句话带过（"XX 说今天吃了火锅——羡慕啊！话说..."）。
  把分散的弹幕串到自己想讲的故事上。

  IMPACT_ESTIMATE: 如果做到，这个片段的互动评分预计提升 1-1.5 分。
  DIFFICULTY: 中等——需要练习"选弹幕"的眼力。
  FIRST_STEP: 明天开播时，给自己加一条规则——每条弹幕只做两种处理：
  要么一句话微笑带过，要么选一条展开讲 1 分钟。不要有"念完就走"的中间态。
  ```
```

### 推理链的好处

1. LLM 的思维是线性的——推理链匹配它的 native 思维模式，输出质量更高
2. 不需要 Pydantic schema 校验——不会因为格式问题触发 auto-fix retry
3. 终端不需要解析——这个文本可以直接展示给开发者，也可以被后面的 LLM 节点消费
4. 只有最终输出（Step 4 教练干预包）需要结构化存储用于跨场对比

### JSON 保留的时机

只有在 Step 5（跨场趋势分析）需要做数值对比的时候，才需要 Step 4 产出结构化数据。中间步骤（Step 1 分片、Step 2 分析、Step 3 聚合、Step 3.5 交叉推理）全部用推理链。

Step 4 的结构化存储只需要保留：
- `session_score`（总分）
- `dimension_scores`（各维度分数）
- `focus_skill`（本期焦点技能）
- `next_step`（第一步）

这几个字段足够支持跨场趋势，不需要把完整的 issue 列表、子评分等全部结构化。

## 改动 7：引入"教练对话"接口

**问题**：当前系统只有一个交互模式——"跑复盘 → 看报告 → 有疑问就去 Q&A"。

但主播看完报告后真正需要的是**对话**，不是**问答**。问答是"我问你答"（像查字典），对话是"你来我往"（像找教练）。

### 新方案：Coach-in-the-Loop 对话界面

在 Step 4 产出教练干预包后，不直接输出一份报告文件，而是进入一个**教练对话界面**。

### 对话示例

```
系统：今天的复盘跑完了。有一个发现可能跟你有关系——直播第 40 分钟左右的时候，
      弹幕突然少了。你当时有感觉到什么不一样吗？

主播：我觉得自己那时候有点没话说了...

系统：对，我能看到你确实有 2 分钟没什么话。这个情况在过去 3 场直播里都出现了。
      要不要一起看看这三场里"没话说"之前的共同点是什么？

主播：好。

系统：注意到前两次没话说的时候，你刚聊完一个需要"动脑子"的话题。
      一次是聊游戏攻略，一次是聊角色考据。这两次聊完后你都有 2-3 分钟的"断档"。
      你平时聊完一个复杂话题后，是怎么切换到下一个话题的？

主播：我就想到什么聊什么...

系统：这个想法本身没错。但"复杂话题 → 自己想到什么聊什么"之间有一道隐性门槛——
      你从"输出信息"模式切换到"闲聊"模式需要 2-3 分钟的大脑缓冲。
      好多主播都有这个坎——不是你没话聊，是你的大脑在切换频道。

      这周试试：下次聊完复杂话题，直接在最后问观众一个选择题。
      比如"好了攻略讲完了——接下来想听我唱歌的扣1，想听我讲故事的扣2"。
      这个提问给你 10 秒缓冲，也给观众一个明确的"现在换台了"的信号。

      想试试吗？

主播：好的我试试！

系统：给你总结一下练习卡片：
      - 这周焦点：复杂话题到闲聊的"桥接"
      - 第一步：聊完硬核内容后，用一个二选一问题过渡
      - 验证信号：提问后 10 秒内 5 人回应
      - 下次复盘时，我会重点看你的"话题切换"环节
      加油！
```

### 对话特性

1. **异步对话**：不是实时聊天机器人。主播什么时候想"找教练聊聊昨天的直播"就什么时候打开
2. **有状态**：对话可以中断再继续（LangGraph checkpoint 支持）
3. **引导式**：教练多用提问少用陈述——让主播自己发现规律，而不是被告知规律
4. **结束即产出**：对话结束 → 自动生成练习任务卡片 + 验证信号列表

### 练习卡片数据结构

对话结束后生成的练习卡片采用以下最小结构化 schema，足够支撑 Step 6 的跨场趋势追踪：

```
{
  session_id: string,        // 绑定的复盘场次
  focus_skill: string,       // 本期焦点技能（如"桥接""选弹幕"）
  first_step: string,        // 30秒可执行的第一步
  verification_signal: string, // 验证信号（如"提问后10秒内5人回应"）
  difficulty: "低" | "中" | "高",
  assigned_date: date,       // 练习任务分配日期
  status: "active" | "completed" | "abandoned"  // 练习状态
}
```

**卡片生命周期管理：**
- 对话中系统提出练习建议后，有一个显式的"确认练习目标"环节——主播可以确认、修改或拒绝练习目标
- 确认后卡片写入 Step 6（跨场趋势存档），状态为 `active`
- 下一次复盘时，Step 6 自动查询该主播的活跃练习卡片，Step 4 教练干预包中增加"上次练习回顾"段落
- 连续 3 场未提及该技能时，卡片状态自动更新为 `completed`

### 直播间的对话并行管理

一场对话绑定一次复盘（session_id），主播对同一场复盘只能有一个活跃对话。对多场不同复盘，主播可以同时发起多个对话——每个对话的状态通过 session_id 隔离，互不干扰。

### 与现有 Q&A 的关系

Q&A 系统保留，但功能重新定位：
- 教练对话：复盘后的引导式对话（深度交互，一次一个话题）
- Q&A：主播自主提问（广度查询，想看什么自己问）

两者互补，不是替代。

**数据共享层设计：**教练对话和 Q&A 共享 Step 6 的跨场趋势数据。具体而言：
- Q&A 可以读取当前活跃的教练对话上下文（本场教练干预包 + 对话历史 + 练习卡片），在主播通过 Q&A 追问"我这周练习的是什么？"时直接引用对话中的目标
- Q&A 的回答中，如果涉及教练对话已覆盖的话题，自动引用教练对话上下文——"根据你上次教练对话中确定的练习目标，你的话题切换能力已经…"
- 共享方式：Q&A 的 prompt 中注入当前活跃教练对话的 checkpoint 摘要（不超过 200 字），通过 LangGraph 的 state 读取接口实现

## 重新设计的完整架构

```
原始直播数据
    │
    ▼
Step 0: Triage（动态维度激活）
    输入：本场统计 + 历史基线
    输出：维度激活矩阵（深度/浅度/跳过）
    │
    ▼
Step 1: 数据分片（不变）
    输出：N 个片段
    │
    ▼
Step 2: 深度维度 → 渐进式调用链
        浅度维度 → 1 次扫描调用
        跳过维度 → 不调用
    ├── Round 1: Observe（观察：发生了什么）
    ├── Round 2: Score（评分：仅 Round 1 有内容时）
    ├── Round 3: Diagnose（诊断：仅评分 ≤ 7 时）
    └── Round 4: Advise（建议：仅有诊断时）
    所有 Round 输出为推理链格式
    │
    ▼
Step 3: 维度内聚合
    各维度汇总跨片段趋势
    │
    ▼
Step 3.5: 跨维度推理层 ✨ 新增
    因果链检测 + 矛盾信号 + 核心驱动维度识别
    输出：因果链路图 + 统一叙事
    │
    ▼
Step 4: 教练干预包生成
    Anchor + Pattern + Focus + FirstStep + VerifySignal
    + WellnessCheck（条件性）+ ExtendedReading（可展开）
    输出：教练干预包 Markdown + 核心字段 JSON（用于跨场对比）
    │
    ├──→ Step 5: 教练对话入口
    │          Coach-in-the-Loop 引导式对话
    │
    └──→ Step 6: 跨场趋势存档
               结构化存储用于长期对比 + 停滞检测 + 倦怠预警
```

### 关键流程变化对比

| 层面 | 当前 | 重新设计后 |
|------|------|-----------|
| 维度激活 | 每场 6 维度全深度 | Triage 后按需激活，可能 2-3 维深度 |
| 分析方式 | 每个维度 1 次 LLM 调用（767 行 prompt） | 深度维度 4 轮渐进调用，每轮 ≤ 100 行 |
| 输出格式 | JSON 贯穿全链 | 中间步骤推理链，最终输出才需结构化 |
| 交叉推理 | Step 4 在 1 次调用中做全部 | Step 3.5 专门承担，Step 4 只做教练语言转化 |
| 最终产出 | 9 章节"成绩单"报告 | 教练干预包 + 对话入口 |
| 交互模式 | 看报告 + Q&A | 教练对话（引导）+ Q&A（查询） |
| 问题优先级 | 严重度驱动（P0/P1/P2） | 因果链杠杆效应驱动 |
| 教练质量 | "如老师"（给评分、给等级） | "如教练"（给锚点、给选择） |

## 优先级建议

### 如果只做一项

**改动 5 + 改动 2（因果链优先级 + 跨维度推理层）**

理由：这是当前架构最大的盲区。在不改变任何现有 prompt 文件的情况下，在 Step 3 和 Step 4 之间插入一个推理节点。产出质量立刻提升——主播收到的建议从"你这个问题很严重"变成"你这个问题是另一个问题的结果"。

### 如果做两到三项

在上述基础上加**改动 3（教练干预包替代成绩单）**

理由：这是从"有用"到"好用"的跨越。输出结构变了，但 Step 1-3.5 的输入不变，可以新旧并行过渡。

### 如果允许全改

实施顺序：
1. **先做跨维度推理层**（新能力，不破坏现有逻辑）
2. **再做教练干预包替代输出结构**（改变输出，但可以新旧并行）
3. **再做动态维度激活 Triage**（节省成本，提高深度维度质量）
4. **最后做渐进式调用链**（最深的重构，但也是最彻底的改进）

### 为什么渐进式调用链放最后

改动 1（渐进式调用链）是 7 项改动中影响面最大的：
- 需要重写 6 个分片分析文件的 prompt
- 需要重写 Worker 调用逻辑（4 轮调用替代 1 轮）
- 增加了调用次数和延迟

但它也是效果最根本的——因为所有其他改动都在"如何消费和使用分析结果"上，而改动 1 在"分析结果本身的信噪比"上。如果分析质量不高（prompt 太长导致注意力稀释），下游再好的推理也弥补不了上游的噪声。

建议策略：前三项先落地验证 → 用验证期间的实战数据评估"当前 767 行 prompt 的输出质量到底怎样" → 根据数据决定是否启动改动 1。如果数据表明当前 prompt 下的分析质量可接受，改动 1 甚至可以推迟到下一个大版本。

## 补充观察：写书项目的方法论反向输入

`写书任务/` 下的三层读者结构（萌新/中层/高层）实际上是一个已被验证的"渐进式披露"实践——你把 767 行的分析框架翻译成中国文化表达，分三层读者，每层只给那个层级需要的信息。

这件事提示了一个**反过来用**的思路：你的写书方法论，可以用回到复盘系统的教练输出设计上。

同一个发现（如"弹幕互动质量低"），对不同层级的主播应该说不同的话：

**新手（<6 个月）：**
"下次试试把'大家今天想聊什么'换成'今天想听我唱歌的扣1，想聊天的扣2'。选择题比问答题好用一百倍。"

**成长期（6 个月-2 年）：**
"你注意到了吗——你每次问开放题后弹幕都会变少。不只是问题本身难，是你的提问时机和话题切换有关。聊完硬核内容后你的大脑需要缓冲，但你直接进入下一个话题了。"

**资深期（2 年+）：**
"你的互动已经很好——现在的问题是'热闹但不深'。试一次：每场只深度回应 1-2 条有故事的弹幕，其他的用一句话带过。你不需要对每条弹幕负责——你需要对'弹幕池的氛围'负责。"

这在教练干预包的输出生成中体现为一个额外的 context 参数 → `streamer_experience_level`，Step 4 根据这个参数调整建议的颗粒度和语言深度。

**`streamer_experience_level` 参数的获取与规则：**

1. **自动计算来源：**取自主播 profile 表中的累计开播时长字段，系统在每次复盘前自动计算更新，无需主播手动标注。

2. **层级判定规则（基于累计开播时长）：**
   - **新手**：< 180 天（约 6 个月）→ 建议侧重"给一句能照着说的话"，用具体话术而非概念
   - **成长期**：180-730 天（6 个月-2 年）→ 建议侧重"让主播理解为什么"，揭示行为模式
   - **资深期**：> 730 天（2 年+）→ 建议侧重"挑战现有框架"，讨论更高阶的策略思维

3. **过渡处理：**层级判定基于开播天数的连续值，不使用硬截止。边界附近（如 170-190 天）主播同时接收两个层级风格的建议，由主播的自然反馈决定下一场使用哪种风格。

4. **影响范围：**层级仅影响 Step 4 的教练语言风格和 Step 5 教练对话的引导深度，不影响 Step 2-3.5 的分析策略——分析应当客观，适配只发生在输出层。
